# 01. 수출통관 업무와 현재 구현 비교

상태: 1단계 비교 완료 / 2단계 핵심 인터뷰 반영 / 1차 명세·작업 목록 작성. 이 문서는 확정 명세나 구현 지시서가 아니다.

## 1. 사용자가 확인한 업무와 프로젝트 동기

현재 수출통관 업무를 수행한다. 선적서류를 받아 B/L·Invoice를 눈으로 확인하고, 필요한 자료를 통관프로그램에 입력해 신고서를 작성한다. 관세청 신고 후 수리를 받으면 수출통관필증이 나온다.

이 중 서류 확인·반복 입력 과정의 자동화 가능성을 개인 프로젝트로 구현하려는 목적이다. 지원 직무는 업무 자동화·솔루션 운영이다. 2026-09-06 사용자 설명으로 프로그램과 기본 입력 흐름, 기존 기록 재사용 방식을 확인했다. 후속 인터뷰에서 Excel을 거친 ecom 일괄 붙여넣기와 12열 순서를 확인했다. 아래 초기 비교의 미확인 사항은 후속 명세의 확인 내용으로 보완한다.

### 확인된 ecom 작업 흐름

1. 선적서류를 확인하고 ecom 업무화면에서 해당 건을 **통관전환**한다.
2. 기존 설정의 고정값이 들어간 신고서 화면이 만들어진다. 필증·가면장에는 약 50~60개 입력공간이 있지만 이를 전부 새로 입력하는 것은 아니다.
3. 공통입력에서 환급신청인, 간이자동정액환급여부, 구매자코드, 목적국, 구매자, 제조자, 거래구분, 결제방법(사용자 표현: 결재방법), 인도조건, 통화단위, 운임비, 기타금액, 총금액, 중량 및 카톤수를 입력·확인한다. 일부는 가장 빈번한 값으로 기본 설정되어 예외일 때만 바꾼다. 정확히 어떤 항목이 기본값인지는 아직 미확인이다.
4. 란 항목에서 세번부호, 품명, 거래품명, 규격, 수량, 단가, 금액, 원산지, 순중량, 원산지코드를 입력한다. 원산지와 원산지코드의 실제 화면상 의미는 아직 구분하지 않았다.
5. 란 분류를 하고 저장한 뒤 관세청에 송신한다.
6. 기존 기록 리스트에서 더블클릭하면 이전 입력정보 일부가 적용된다. 적용되는 정확한 필드와 HS 재사용 방식은 아직 확인하지 않았다. 사용자 설명상 업무는 여전히 수기 입력 중심이다.

### 범위에 대한 판단

- 우선 대상: 통관전환 이후 남는 공통항목·품목 입력과 란 분류를 돕는 과정. 구체적 구현 범위는 서류 출처와 분류 기준, ecom 전달 방식 확인 후 확정한다.
- 관세청 송신 자동화는 우선 범위에서 제외한다. 사용자는 API가 없어 전체 자동화를 포기했다고 설명했으며, 기존 프로그램의 일괄송신으로 끝나는 단계라 중요도가 낮다고 했다. 이는 사용자 경험이며 관세청 API 제공 여부를 조사한 결론은 아니다.
- 자체 CSV/XLSX/XML 생성만으로 ecom 입력 자동화를 달성했다고 볼 수 없다. 파일 불러오기나 붙여넣기 등 실제 연결 방법과 재입력 감소를 확인해야 한다.
- 과거 ecom/LV1 관련 기록에 있던 UPS 업무 흐름을 이번 대표 업무로 간주하지 않는다. 이번 범위는 현재 사용자가 설명한 흐름을 기준으로 정한다.
- 사용자 참고 링크: https://m.blog.naver.com/eco275/222110406474 . 접근 시 브라우저 사이트 보안 정책으로 차단되어 본문 미확인. 위 사실의 출처는 사용자 설명이다.

## 2. 비교 근거와 한계

- 로컬 `전자문서항목정의서_수출신고서(830).xlsx`의 `항목정의서` 시트 B열 항목명, E열 조건, I열 설명, O열 XPath를 읽었다. 아래 행 번호는 이 시트 기준이다.
- 로컬 `[수출]수출신고서_GOVCBR830.hwp`의 파일 존재를 확인했다. HWP 본문·화면 배치를 읽은 것은 아니다. 이번 필드 비교는 XLSX를 기준으로 한다.
- 저장소 `backend/app/services/customs_schema/`의 XSD 헤더는 Last change를 2017.10.23으로 표기한다. XSD가 참조하는 공통 스키마 두 경로가 현재 저장소에 없다. 최신 공식 규격 적합성을 확인한 것은 아니다.
- 코드 근거: `backend/app/models/declaration.py`, `models/company_settings.py`, `services/parser/{base,pdf_parser,excel_parser}.py`, `services/mapper.py`, `services/validator.py`, `services/xml_generator.py`, `services/submission/file_export.py`, `api/invoices.py`, `frontend/src/pages/DeclarationEdit.tsx`.
- 실제 고객 문서·DB는 비교 입력에 사용하지 않았다. 출력 확인에는 이름·국가·금액 등을 임의로 만든 합성 객체만 사용했다.
- 항목정의서의 M/C는 로컬 자료의 표기를 기록한 것이다. 신고 유형별 적용 조건이나 현재 법적 필수 여부를 여기서 확정하지 않는다.

## 3. 실제 업무 단계와 구현

| 업무 단계 | 현재 구현 | 실무 확인이 필요한 부분 |
|---|---|---|
| 선적서류 수령 | PDF/XLSX 파일 1개 업로드 시 신고서 초안 1개 생성 | 한 건당 파일 구성, PDF가 스캔인지 텍스트인지, 여러 Invoice가 있는지 |
| B/L·Invoice 확인 | 인보이스 키워드·표 파싱. B/L 전용 파서와 문서 간 대조 흐름 없음 | B/L에서 실제 가져오는 항목, Invoice와 값이 다를 때 처리 |
| 통관프로그램에 신고서 작성 | 자체 화면에서 초안을 수정하고 저장 | ecom 통관전환·기본값·기존 기록 일부 재사용 및 Excel에서 일괄 붙여넣기 사용 경험 확인. 현재 앱 출력의 실제 호환성은 미검증 |
| 관세청 신고 | CSV/XLSX/XML 출력. 선택적 외부 연계 코드는 있으나 실제 접수 검증 없음 | 사용자 요청상 송신 자동화는 우선 제외. ecom 입력까지의 연결 방식 확인 필요 |
| 수리·필증 발급 | 상태·조회 관련 코드가 있으나 실제 업무 처리·필증 발급 검증 없음 | 우선 자동화 범위에 포함할 근거는 아직 없음 |

## 4. 필드 비교

원본 출처 후보는 실무 확인을 위한 가설이다. B/L·Invoice에 항상 해당 값이 있다는 뜻이 아니다.

| 항목 / 정의서 행 | 현재 파싱·입력 | 현재 XML 출력·차이 | 실무 확인할 출처 후보 |
|---|---|---|---|
| 수출화주·구매자 상호 / 60, 78 | Seller/Shipper/Exporter, Buyer/Consignee/Importer 등 키워드로 이름 추출 | 화주·구매자 Name으로 출력. 문서상의 당사자와 신고상의 당사자가 같은지는 별도 확인 필요 | Invoice, 거래처 등록정보 |
| 사업자번호·통관고유부호·주소·대표자 / 53–75 | 일부 신고서 입력과 회사 설정. 주소 자동 추출은 구현 안 됨 | 설정이 신고서 값보다 우선하는 곳이 있음. 신고인과 수출화주 대표자에 같은 설정 사용 | 거래처 등록정보, 이전 신고 |
| 제조자 / 72–75 | 독립 입력 모델 없음 | Manufacturer 출력 없음 | 거래처 정보, 건별 확인 |
| 목적국 / 15 | buyer_country_code와 destination_country_code를 별도 입력. 둘 다 자동 추출 안 됨 | 정의서의 목적국 위치에 buyer_country_code 출력. destination_country_code는 XML에 사용 안 됨 | B/L·Invoice 중 실제 기준 확인 |
| 적재항 / 16–17 | 수동 입력 또는 회사 설정 | 설정 우선 출력, 적재항구분은 6으로 고정 | 운송서류, 등록 기본값 |

| 신고세관·과·물품소재지 / 13–21 | 세관 코드 회사 설정. 독립 과·소재지 모델 없음 | 소재지 요소가 비어 있음 | 회사·거래처 설정, 건별 소재지 |

모든 미구현 항목을 개발할 필요는 없다. 대표 업무 한 가지와 첫 산출물을 정한 뒤 필요한 항목만 명세에 포함한다.

## 5. 합성 객체로 확인한 현재 동작

입력: 구매자국가 US, 목적국 CA, 결제방법 TT, 전체 순중량 7.5kg, 총중량 8kg, 금액 25.50 USD, 품목 1건, HS 미입력.

| 확인 대상 | 실제 결과 |
|---|---|
| 필드 검증 | 오류 목록 비어 있음. HS 누락을 차단하지 않음 |
| 목적국 XPath | US 출력. 별도 입력 CA는 반영 안 됨 |
| 결제방법 XPath | 빈 문자열 |
| 란별 순중량 XPath | 0 |
| 원산지 XPath | 입력하지 않았는데 KR |
| UCR XPath | 합성 Invoice 번호 SYN-COMPARE-001 |
| 전자문서 기능 | 1 |

이 확인은 현재 함수를 직접 호출한 재현이며 새로운 회귀 테스트를 추가한 것은 아니다. 이전 30개 테스트 통과는 그 테스트의 범위를 증명한다. 신고서 의미와 값 전달의 완전성까지 증명하지 않는다.

CSV/XLSX는 내부 모델 값을 옮기는 자체 출력 구조다. 통관프로그램의 실제 파일 불러오기를 확인하기 전에는 해당 프로그램용 호환 파일이라고 설명할 수 없다.

## 6. 후속 인터뷰와 1차 범위

확인된 전체 업무와 출력 규칙은 [02 명세](ecom-preparation-spec.md), 실행 순서는 [03 작업 목록](ecom-preparation-tasks.md)에 정리했다.

- ecom에 Excel의 데이터를 일괄 붙여넣는 기존 경로가 있다. 사용자는 Gemini 출력→Excel→ecom 흐름을 직접 사용했다.
- 출력은 규격1/규격2/규격3/수량/단가/금액/FTA발급여부/FTA발급협정코드/세번부호/품명/거래품명/순중량의 12열이다.
- 규격 배치는 자유이며 Description에 부품번호 등이 포함된다. 순중량은 대부분 빈칸, 필요 시 수기 입력한다.
- 세번부호·품명·거래품명은 체감상 95% 서류, 5% 판단이다. FTA는 문구·증명서 등을 확인해 판단하며 Y일 때 코드를 넣고 N일 때 코드 칸을 비운다.
- 주 입력은 기존 프로그램이 GIF들을 합친 이미지 PDF이며 PDF·Excel도 받는다. ecom에서 PDF를 열면 기본 OCR이 실행됐다. 결과에 만족하지 못해 사용자는 별도 Chrome OCR 확장프로그램을 설치하고 영역을 직접 선택했다.
- 란 분류는 ecom이 옵션에 따라 수행한다. 정확한 옵션·길이 제한은 기억이 불확실하다.

사용자 정정에 따른 목표는 PDF 인식→공통·란항목 전체 자동 작성→ecom 적용·분류·저장으로 송신 직전까지 준비하는 것이다. 이전의 12열 복사 한정 범위는 assistant의 잘못된 축소였다. 관세청 송신 자체는 제외한다. 새로운 기능이나 GitHub 이슈를 이번 문서 작업에서 만들지는 않았다.
